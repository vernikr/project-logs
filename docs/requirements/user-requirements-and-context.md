# Требования и контекст от владельца

Этот файл объединяет только то, что было сформулировано владельцем проекта в сообщениях. В него не
включены решения, рекомендации и выводы агента.

## Цель

Нужен отдельный проект для продумывания и реализации единой точки доступа к логам пет-проектов.

Желаемый результат:

- иметь для большинства или всех проектов единую архитектуру логирующей системы;
- не продумывать логирование заново для каждого проекта;
- разворачивать логирование в новых проектах с минимальными усилиями;
- облегчить агенту, который работает сразу с несколькими проектами, доступ ко всем логам;
- использовать преимущества наличия собственного сервера;
- обеспечить облачным агентам доступ к серверу, поскольку им проще получить доступ к серверу, чем к
  локальному компьютеру.

## Контекст использования проектов

- Владелец пока является единственным пользователем проектов.
- Разработку, документацию и ведение проектов выполняет ИИ.
- Человек ставит цели и пользуется результатом.
- Человек не читает код и описания PR.
- Человек не проверяет результат после каждого хода.
- Единственная форма контроля — тестирование в ходе реальной работы с продуктом, когда до неё доходит.
- Спринтов нет.
- Разработка не привязана ко времени: за день может быть сделано больше, чем потом за месяц.

## Приоритеты

Приоритеты были сформулированы в таком порядке:

1. Экономия контекста ИИ-агента.
2. Скорость работы агента.
3. Минимизация количества шагов агента.
4. Удалённый доступ для агентов.
5. Минимум интеграционной работы для подключения нового проекта.

## Инфраструктура и финансовые ограничения

- У владельца есть собственный сервер.
- Конфигурация сервера была предоставлена отдельным файлом.
- За ключ из конфигурации сервера просить не нужно: ключ временный и забекаплен.
- Домена сейчас нет и, вероятно, не будет.
- Дополнительно платить за какие-либо решения владелец не готов.
- Исследование по доменам, сертификатам и внешнему доступу показалось владельцу подтверждающим, что с
  внешним доступом проблем быть не должно; это нужно учитывать в архитектуре.

## Содержимое логов и срок хранения

- В логи можно писать всё подряд, включая контент.
- Допустимы длинные тексты, изображения и файлы.
- При протухании контент желательно каким-либо образом схлопывать или сжимать, если это возможно.
- Удаление допускается либо по времени, либо при превышении размера.
- Окончательное решение между удалением по времени и по размеру пока не принято.

- на email;
- в Telegram.

## LLM для обработки логов

- Модели Gemini Flash и выше для обработки логов выделяться точно не будут из-за маленькой квоты.
- Gemini Flash Lite можно рассмотреть.
- Gemma, вероятно, допустима, но есть сомнение, что у неё может быть недостаточно хорошая логика.
- LLM вообще не является обязательной частью системы обработки логов.

## Ожидания от интерфейса расследования

- Не хочется обязательного проектного поля с готовой фразой вроде `answer`, если для его формирования в
  каждом проекте придётся отдельно писать и поддерживать композицию текста.
- Агент и так может увидеть в исходной выборке успехи, ошибки, частичный результат и fallback.
- По поводу автоматических `next_queries` окончательного мнения пока нет.
- Многие логические шаги агент, вероятно, сможет сделать сам.
- Готовые подсказки могут быть полезны только если небольшое увеличение контекста действительно сокращает
  число шагов рассуждения и обращений.

## Привычность интерфейса для агента

- Интерфейс доступа к хранилищу должен быть приблизительно привычен агенту и понятен интуитивно.
- Агент должен иметь возможность отправлять собственные SQL-запросы.
- Нельзя строить интерфейс так, чтобы агент был обязан пользоваться только заранее подготовленными
  специальными командами.

## Структура данных проектов

- У каждого проекта могут быть свои отдельные поля в базе.
- Неясно, должны ли это быть отдельные базы данных для проектов или представления общей базы.
- Общая архитектура должна учитывать, что структура логов часто дорабатывается по ходу работы над проектом.
- Агент может обнаружить, что данных недостаточно для анализа бага, после чего начать логировать подробнее.
- Добавление новых деталей логирования не должно требовать заранее полностью фиксировать структуру всех
  возможных событий.

## Предпочтительный порядок пилота

В пилоте желательно исследовать проекты в таком порядке:

1. `tldr-digest`;

## Форматы логов и доставки в контекст агента

Формат первичного лога на клиенте пока не выбран. Рассматриваются, в частности:

- TSV;
- NDJSON;
- непосредственная запись в SQL;
- другие форматы.

Есть предположение, что формат первичного лога может быть близок к формату, который агент потом будет
читать, чтобы агент привыкал к одному формату и не требовалось много разной логики для записи и чтения.
Это пока мысль для проверки, а не принятое решение.

В пилоте желательно исследовать разные форматы доставки логов в контекст агента и разные советы по их
обработке в `AGENTS.md` или MCP, например:

- TSV и нативное чтение самим агентом;
- logfmt и `ripgrep`;
- NDJSON и `jq`/`ripgrep`.

Вопрос о том, являются ли такие варианты просто адаптерами одного хранилища, также нужно исследовать.

## Порядок полей

Есть предположение, что порядок полей нужно оптимизировать:

- поля, которые чаще бывают пустыми, помещать ближе к концу;
- более плотные поля помещать ближе к началу.

Предполагается, что это может регулироваться как мягкий регламент через инструкции в `AGENTS.md`, но
окончательное решение не принято.

## Версия клиента

В логах должна присутствовать версия клиента, который отправил лог.

## Решения, принятые после анализа внешних предложений

- Доступ к raw-артефактам через публичный HTTPS пока не решён.
- Независимое периодическое резервное копирование пока отложено.
- Прямую отправку логов из UI iframe Figma через HTTPS желательно исследовать в пилоте.
- При этом экспорт журнала Figma должен оставаться резервным вариантом.

## Процесс работы на текущем этапе

- Пока нужно анализировать предложения и архитектуру.
- Разрабатывать систему пока не нужно.
